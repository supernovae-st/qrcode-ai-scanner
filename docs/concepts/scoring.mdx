The score answers one question: **how much margin does this code have
before it stops scanning in the real world?**

<Info>
A judgment is whole or absent. A present `score` ran every planned stress
cell, so no wall-clock budget moves it. A judgment the budget interrupts is
`score: null` with `trace.budget_exhausted: true` — "not judged", never a
zero: re-scan with a larger budget or `0` (unbounded).
</Info>

## The composite (0-100)

> **In plain words:** six ways a QR gets harder to scan, each scored out of 5;
> the weakest ones pull the total down, two fatal flaws cap it outright, and
> a used-up error-repair budget caps it too.

Six stress axes, each a ramp of increasingly hostile transforms; survival
stops at the first failed cell (the knee). Weighted sum → structural caps
→ UEC margin cap → grade band.

| Axis | Weight | What it stresses |
|---|---|---|
| resolution | 22 | sampling margin (px/module floor) |
| blur | 18 | focus / motion margin |
| contrast | 15 | module/background separation |
| perspective | 20 | grid estimation under tilt |
| rotation | 10 | non-cardinal angles |
| lighting | 15 | shadows, glare, exposure defects |

Two structural caps override everything: a dead finder pattern caps the
score at **40**, a violated quiet zone at **60** — the two documented
AI-art killers. A thin error-correction margin `m` below 0.5 caps it
continuously at `round(40 + 120·m)` (0.25 → 70 · 0 → 40): a consumed
repair budget is invisible to the stress axes.

<Info>
Survival is measured relative to the symbol's **own decode class**: an
artistic symbol that only decodes through a deep rung is stress-tested
with that rung. "Fragile" is never conflated with "undecodable".
</Info>

Bands: `excellent` ≥80 · `good` 70-79 · `acceptable` 60-69 · `fair`
40-59 · `poor` &lt;40. A verify meter can map ≥80 → HIGH, 60-79 →
MEDIUM, decoded &lt;60 → LOW, none → NO, and a decode the budget left
unjudged → NOT_JUDGED (never LOW) — the pattern of the
[Nuxt verify guide](/guides/nuxt-verify).

## The synthetic UEC (`score.uec`)

> **In plain words:** how much of the QR's built-in error-repair budget is still
> unused. A full tank (margin 1.0) is healthy; an empty one (0) means the decode
> sat at the edge and might be wrong.

The ISO 15415 *Unused Error Correction* margin, computed from the
engine's own sampled bitstream: unmask → de-interleave → Reed-Solomon
syndromes → Berlekamp-Massey degree = the EXACT number of codewords the
decode had to correct. The stream is the one of the orientation the decode
verified (a mirrored code is measured mirrored-back, and reads the same
margin as its upright twin), and a margin is read only when every block
error-corrects errors-only — otherwise there is no `uec`, no cap and no
margin hint. A stream the rescue stage recovered keeps its own
errors-only count: with `rescue` among the engines, `worst_block_errors`
is a distrust marker (typically margin 0), not the errors it corrected.
Skipping the `uec` check withholds the section and its two hints, never
the cap: the value does not move.

```json
"uec": { "margin": 0.82, "grade": "a",
         "worst_block_errors": 2, "worst_block_capacity": 22 }
```

`margin = 1 − 2t/d` over the worst block (`d` its parity codewords).
**Margin 0 is special**: the block's errors spent all its parity (on a
rescued read, the distrust marker above). This is a distrust signal,
not proof of a *miscorrection* (a decode that looks valid but is wrong). The
`low_correction_margin` hint fires; treat the content as unverified.
The public zxing `qrcode-2/13.png` observation reads "photography" while
the pinned upstream text reads "photograph". Its truth provenance remains
disputed, so this conflict is not a qualified miscorrection example.

<Note>
ISO 15415 measures this parameter against `d − p`, where `p` codewords
are reserved against misdecodes on version 1, v2-L and v3-L. The margin
does not subtract them, so on those symbols a block with errors reads
above ISO's value: for an errors-only decode at the acceptance limit,
where ISO reads 0, it reads 0.059 to 0.43, caps the score at 47 to 91
instead of 40 and raises no `low_correction_margin` — there, no hint is no
proof. The table:
[`spec/04-score.md`](https://github.com/supernovae-st/qrcode-ai-scanner/blob/main/spec/04-score.md)
§ Synthetic UEC.
</Note>

## The ISO 15415-informed grade card (`score.iso15415`)

> **In plain words:** the same A–F parameters a commercial barcode verifier
> reports, computed in software — useful diagnostics for *what to fix*, never a
> certified grade (that needs calibrated hardware).

A per-parameter verifier-style card whenever geometry was measured —
each `{value, grade}` in the official ISO bands, `overall` = the lowest
measured parameter (the ISO rule; a withheld `unused_error_correction`
still counts):

```json
"iso15415": {
  "symbol_contrast":        { "value": 1.0,   "grade": "a" },
  "modulation":             { "value": 1.0,   "grade": "a" },
  "axial_nonuniformity":    { "value": 0.001, "grade": "a" },
  "fixed_pattern_damage":   { "value": 1.0,   "grade": "a" },
  "unused_error_correction":{ "value": 1.0,   "grade": "a" },
  "overall": "a"
}
```

<Warning>
**The honesty line.** A *certified* ISO 15415 grade requires calibrated
optics (45° illumination, stated wavelength, defined aperture) and
ISO/IEC 15426-2 hardware conformance — properties of a verifier device.
This card is **standards-based diagnostics**: same bands, algorithms
approximated in software (the UEC omits the misdecode reserve `p`,
above), uncalibrated capture. Parameters that need the hardware (Grid
Nonuniformity, Reflectance Margin) are reported absent, never faked.
If a customer needs a certificate, they need a hardware verifier — this
scanner tells them *what to fix first*.
</Warning>

GS1 conformance is different — pure syntax, fully software-checkable:
see [GS1](/concepts/gs1).

Full normative tables (weights, ramps, bands, caps):
[`spec/04-score.md`](https://github.com/supernovae-st/qrcode-ai-scanner/blob/main/spec/04-score.md).
